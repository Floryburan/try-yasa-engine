# 结果解释

这组数值来自静态规则推导的 AI 辅助参考标注，未做独立人工逐点复核。规则按源码导入、URL/CLI 绑定、独立入口参考及表达式位置推导标签；不是另一轮 LLM 对 6,036 个位置的独立评审。因此分数只能表述为“相对此参考的候选级效果”，不能当作真实部署准确率。

主结果按去重后源码位置计算，避免同一辅助函数在多个入口出现时重复增加大量 TN：

- Accuracy 97.52%，Precision 95.60%，Recall 71.70%，F1 81.94%，Balanced Accuracy 85.70%。
- 参考已定 5,451 / 6,036 个位置，覆盖率 90.31%；585 个参考 unknown 排除。
- 已定参考中，424 个 source、5,027 个非 source。
- TP 304、FP 14、FN 120、TN 5,012，另有 1 个参考已定但模型 unknown 的位置。
- 模型总共 4 个 unknown，其中另外 3 个的参考也为 unknown。
- 原始 318 个模型 yes 都获得已定参考标签；没有通过排除参考 unknown 隐藏尚未验证的模型 yes。
- 全部预测 no 的准确率基线为 92.22%；类别不均衡使 Accuracy 明显高于检出 source 的召回率。

误报 14 个中：

- 7 个是字段获取后的 `.strip()` 等处理调用。主参考把更内层的输入读取视为 source，把外层处理视为传播。
- 7 个是请求承载参数上的后续读取，例如插件方法的 `request.form`、`request.get_json()`。主参考认为参数已经引入输入，后续读取不是新的起点。

漏报 120 个中：109 个属性读取、6 个调用返回值、3 个下标读取、2 个请求承载参数。
常见表达式为 `request.form`（39 个）、`request.args`（32 个）、`request.method`（25 个）。
这里按精确 AST 位置评分：同一行的 `request.args` 和 `request.args.get(...)` 可以是两个候选；模型只选择其中一个时，另一个仍会计为 FN。
因此 120 个 FN 不等于漏掉了 120 种独立的外部输入，分数也包含表达式定位粒度差异。文件、行、列及参考理由均保存在 CSV 中。

若采用预先定义的“直接请求读取也算 source”辅助口径，Precision 97.80%、Recall 71.66%、F1 82.71%。
该对照不替代主结果，也没有修改 Jev 原始标签。

单独对照 YASA 漏洞报告的 16 个 source：精确位置匹配选中 2 个、匹配但判 no 7 个、未进入本轮候选 7 个，位置重现率 12.5%。
这不是 source 召回率：YASA 采用更宽的 source 规则，并且此表只覆盖已产生告警的路径，既非完整正例集也非完整负例集。
不能把其余 316 个 Jev source 算成误报，也不能从这 16 个位置计算 Accuracy 或 Precision。
